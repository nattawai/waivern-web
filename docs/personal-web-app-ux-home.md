## 3. พฤติกรรม to-do บนหน้า Home

| การกระทำ | Home | หน้า To-do |
|---|---|---|
| ดูรายการ | ✅ **เฉพาะวันนี้** | ✅ **รายเดือน** |
| ติ๊กว่าเสร็จ | ✅ | ✅ |
| ยกเลิกติ๊ก | ✅ | ✅ |
| ดูรายละเอียด | ✅ **กางในที่ ไม่เปลี่ยนหน้า** | ✅ |
| สร้างใหม่ (รวมสร้างล่วงหน้า) | ❌ | ✅ **ที่เดียว** |
| แก้ข้อความ/รายละเอียด | ❌ | ✅ **ที่เดียว** |

**กฎที่สรุปได้:** เปลี่ยน *สถานะ* ได้ทุกที่ · เปลี่ยน *เนื้อหา* ได้ที่เดียว

**ติ๊กแล้วเกิดอะไรขึ้น:** จางลง + ขีดฆ่า · **อยู่ที่เดิม ไม่หายไป ไม่ย้ายตำแหน่ง**

## 4. ผลที่ตามมาทางเทคนิค (ต้องจำตอนเฟส 5-7)

1. 🔴 **หน้า Home ไม่ใช่หน้าอ่านอย่างเดียว** — การติ๊กเสร็จคือการเขียนข้อมูล
   → endpoint นั้นต้องมี **row-level authorization** และต้องมี test พิสูจน์ว่า user A ติ๊กของ user B ไม่ได้
2. หน้า Home ต้องรองรับ 2 สถานะในหน้าเดียวกัน (ล็อกอิน / ไม่ล็อกอิน) ตั้งแต่ตอนออกแบบ ไม่ใช่มาเติมทีหลัง
3. การซ่อนเมนูเป็นเรื่อง **หน้าตา ไม่ใช่ความปลอดภัย** — API ต้องบล็อกด้วยตัวเองเสมอ
4. ราคาน้ำมันใน v1 = **การ์ดเปล่าวางที่ไว้** ยังไม่ดึงข้อมูลจริง (ของจริงอยู่ v2 · ต้องใช้ Cron Trigger + API ภายนอก)

## 5. การสมัครสมาชิก

**ไวเลือก:** ใครก็สมัครได้ **แต่ในทางปฏิบัติจะเป็นการส่งลิงก์ให้** เพราะหน้า login ไม่มีปุ่ม register

🔴 **ข้อควรรู้:** ใช้ Google SSO อย่างเดียว แปลว่า **ปุ่ม "เข้าสู่ระบบด้วย Google" ทำหน้าที่เป็นปุ่มสมัครไปในตัว**
การไม่มีปุ่ม register จึงไม่ได้กันใครเลย — ใครก็ตามที่เปิดหน้า login แล้วกดปุ่มนั้น จะได้บัญชีทันที

**v1 ตัดสินใจ: เปิดตามนั้น ไม่ใส่ประตูกั้น** เพราะ
- ต้นทุนการทำประตูกั้น (invite token / allowlist / รออนุมัติ) = หลายวัน
- ความเสี่ยงจริงต่ำมาก — สมาชิกที่หลุดเข้ามาทำได้แค่สร้าง to-do ของตัวเอง
- เติมประตูกั้นทีหลังได้โดยไม่ต้อง migration ข้อมูลเดิม (เพิ่มการตรวจตอน callback + ตาราง token)

**ตัวเลือกที่เก็บไว้พิจารณาใน v2 ถ้าเริ่มมีคนแปลกหน้าสมัครจริง:**
- invite token (`?invite=xxx`) · allowlist ตามอีเมล · หรือสมัครได้แต่ role = pending รอไวอนุมัติ

**บรรทัดอธิบายใต้ชื่อเว็บ:** ✅ ใส่ — แต่เป็น **คำอธิบายว่าที่นี่คืออะไร ไม่ใช่คำเชิญชวนให้สมัคร**
ตัวอย่างโทน: *"แพลตฟอร์มส่วนตัว — จัดการ to-do และติดตามราคาน้ำมัน"*

## 6. ยังไม่ตัดสิน (ค่อยตอบตอนวาด)

- ข้อความจริงของบรรทัดอธิบายใต้ชื่อเว็บ
- Lore บนหน้า Home จะโชว์เต็มหรือย่อ + ปุ่มอ่านต่อ
- to-do วันนี้ ถ้าไม่มีสักรายการ จะแสดงอะไร (empty state)
- ถ้าวันนี้มี to-do 20 รายการ จะตัดที่กี่รายการ

## 7. Navbar — เคาะ 2026-08-31

**กฎที่ไวออกแบบ:**

| สถานการณ์ | navbar |
|---|---|
| หน้าสั้น ไม่ต้องเลื่อน | **normal** (แถบเต็มความกว้าง) |
| หน้ายาว · กำลังเลื่อน | bubble (ลอย) |
| หน้ายาว · เลื่อนถึงล่างสุด | normal |

🔴 **การสลับสถานะ = v2** (ต้องฟัง scroll + ทำอนิเมชัน)

**ผลที่ตามมาสำหรับ v1:** หน้าใน v1 เกือบทั้งหมดสั้นจนไม่ต้องเลื่อน (Home ~840 · Login · 404) → **v1 ใช้ normal navbar อย่างเดียวทุกหน้า** เป็นข้อสรุปที่ตามมาจากกฎข้อแรกโดยตรง ไม่ใช่การตัดทิ้งเพื่อความง่าย

## 8. กฎข้ามหน้า — เคาะ 2026-08-31

กฎ 2 ข้อนี้ใช้กับ **ทุกหน้า** ไม่ใช่เฉพาะ Home

### 8.1 เมนูนำทางแสดงเฉพาะคนที่ล็อกอินแล้ว

| ส่วน | ยังไม่ล็อกอิน | ล็อกอินแล้ว |
|---|---|---|
| navbar | มีแค่ปุ่ม **เข้าสู่ระบบ** | เมนู to-do · ราคาน้ำมัน · โปรไฟล์ |
| **footer** | Lore · Contact | Lore · **Footer Menu** · Contact |

**เป็นกฎเดียวกันทั้งสองที่** — เมนูนำทางทุกชนิดโผล่เมื่อล็อกอินแล้วเท่านั้น
→ ไม่ต้องตัดสินใจใหม่ทุกครั้งที่เพิ่มเมนูหรือหน้าใหม่

**footer จึงเป็นชิ้นส่วนที่มี 2 สถานะ** เหมือน navbar — ไม่ใช่ความไม่สม่ำเสมอ
เฟรม `03-privacy-*` และ `04-404-*` ที่วาดไว้คือ **สถานะ guest** · สถานะ auth ต่างกันแค่มี Footer Menu เพิ่มมา 1 ชิ้น จึงไม่ต้องวาดเฟรมเพิ่ม

### 8.2 หน้าเสริมไม่มี navbar — มีแค่ทางกลับ (ไวยืนยันว่าตั้งใจ)

| ประเภทหน้า | ด้านบน | หน้าไหนบ้าง |
|---|---|---|
| หน้าเนื้อหาหลัก | navbar เต็ม | Home · To-do |
| **หน้าเสริม** | **`< BACK` อย่างเดียว** | Login · Privacy Policy · 404 |

**เหตุผล:** หน้าเสริมมีงานให้ทำอย่างเดียว (เข้าระบบ / อ่านนโยบาย / กลับออกไป) การมีเมนูเต็มทำให้ไขว้เขว
**กฎที่ตามมา:** หน้าใหม่ในอนาคตที่เป็นหน้าเสริม ให้ทำตามแพทเทิร์นนี้ — และ **ทุกหน้าต้องมีทางออกอย่างน้อย 1 ทางเสมอ**
